# Architecture: what's what in `EndlessMode/src`

About 8,000 lines of C++20. One DLL, no engine SDK: everything the mod does to the game goes through functions it finds by
signature and structures whose layouts were reverse-engineered (documented in [GAME_INTERNALS.md](GAME_INTERNALS.md)).

## Lifecycle and threads

Overstrike's scripts proxy calls `LoadLibrary` on the DLL, then the exported `script_enable()` (`main.cpp`). That is very
early in game startup, before the world exists, so `script_enable` only spawns a worker thread.

```
script_enable()  ->  Main thread (main.cpp)
   1. open the log, resolve natives (natives::ResolveAll)
   2. gamethread::Install()  -- hook the game's per-frame function; later jobs run on the game thread
   3. stats::InstallHooks(), guards::Install(), gfx::InstallTextCapture()
   4. portal::Start()        -- starts the portal thread
   5. loop forever: poll EndlessMode.cmd every 250 ms (dev commands)
```

| Thread | Started by | What it does |
|---|---|---|
| **Game thread** (the game's own) | the hook in `gamethread.cpp` | Runs queued jobs, one batch per frame. All writes to game state happen here |
| **Main/command thread** | `script_enable` | Command-file polling (`main.cpp`) |
| **Portal thread** | `portal::Start` | Every 100 ms: input, dock circles and panels, the abandon prompt, travel, results panel, arena fence |
| **Director thread** | `director::Start` | A run: spawning, waves, scoring, boons. Runs only while a run is going |
| PlayStation HID thread | `psinput::Start` | Reads DualSense/DualShock buttons directly (the game talks to them natively, XInput never sees them) |
| Short-lived threads | various | Post-run asset release (30 s after a run), loadout restore |

Rule: **a worker thread never touches game memory writes or game functions directly.** It calls
`gamethread::Run(fn, timeout_ms)` (blocks until the game thread ran it) or `gamethread::Post(fn)` (fire and forget). Reads go
through `memory.h` so a bad pointer returns false instead of crashing the game.

## Module map

### Core plumbing

| File | Role |
|---|---|
| `main.cpp` | Entry point, the command-file poller, and every dev command (a big `if` chain on `cmd == "..."`) |
| `log.*` | `LOG(...)` to `EndlessMode.log`, truncated each launch |
| `paths.h` | The scripts folder (where the DLL lives) |
| `scan.*` | Signature scanner over the game's `.text`; "48 8B ?? E8" patterns, rip-relative decoding |
| `natives.*` | The table of game functions/data: each has a signature and an **expected RVA**; resolves only if both agree. Includes typed wrappers (`SpawnRaw`, `LoadAssetByHash`, `AssetRelease`, ...) |
| `memory.*` | Guarded reads and writes (`memory::Read`, `Write`, `SafeCall`; structured exception handling) |
| `gamethread.*` | The per-frame hook (`exe+1f745f0`) and the job queue; tick-rate/frame-time proxy |
| `guards.*` | Patches a null check into game code that assumes mission context (bosses outside missions crashed in `BotStateGotoLocal`) |

### Game objects

| File | Role |
|---|---|
| `entity.*` | Entity layout: transform, components by name, handle <-> entity, finding the bot's `BotData` |
| `spawn.*` | Load an actor asset by path (reference counted), spawn it engaged with the hero, despawn; preload/release; waits for model dependencies |
| `damage.*` | Sends a real damage message through the game's own pipeline (so enemy awareness reacts like a real hit) |
| `events.*` | The engine's event system and bot groups (alerting a group, etc.) |
| `inventory.*` | The hero's inventory: add/remove/query items by config asset id; item name/description text |
| `runloadout.*` | Saves the player's suit power and mods, empties and locks the slots for a run, restores afterwards (crash-safe via a file) |
| `timescale.*` | World time scale through the game's `TimeScaleSystem` (slow motion, freeze while picking rewards) |
| `camscan.*`, `watchpoint.*`, `observer.*` | Research tools: find the camera by memory scanning, a hardware write watchpoint on all threads, pass-through hooks that log what the game spawns/loads |

### Game content

| File | Role |
|---|---|
| `roster.*`, `roster_data.inc` | Factions (9), their units (actor path, role, class, health) and bosses. `roster_data.inc` is **generated** by `tools/roster/gen_roster.py`; don't hand-edit |
| `preload_deps.inc` | Generated by `tools/assets/deps.py`: extra actors (weapons, jetpacks, heads) each unit creates at runtime and that must be loaded too |
| `plan.*` | **Pure** wave planning: given config + wave number + rng, the goons, mix, caps, bosses and title. Testable offline (`tests/run_plan.cmd`). Also Horde's level curve, faction rotation and the unit-type budget |
| `director.*` | Executes plans. Countdown, spawn rings, kill detection, cleanup, culling bodies, stationary-enemy handling, boss watchdog, wave/chapter banners, run end. Two loops: `Run` (Campaign/faction/boss rush) and `RunHorde` |
| `arena.*`, `rykers_points.h` | Arena definitions (the Ryker's yard fence, start line, arrival point, 139 designer spawn points), teleport, zone streaming for interiors |
| `boons.*`, `boon_items.inc` | The roguelike layer: offers 1 of 3 after each wave, applies suit powers/mods/stat boons and curses, uses the game's own names and descriptions |
| `score.*` | Horde style meter, ranks, combo bonus, survival bonus, tier thresholds, history files; Campaign summary |
| `stats.*` | Telemetry: hooks hero damage, writes `EndlessMode_runs/run_*.json` every 10 s |
| `stress.*` | Stress test: how many enemies can the game take |

### UI and input

| File | Role |
|---|---|
| `ui.*` | Calling ActionScript methods on the game's HUD movies, finding HUD elements |
| `hud.*` | Friendly wrappers: notification box (`Show`), medium banner (`Banner`), big countdown, counter |
| `gfx.*` | Building Scaleform data objects from code, `Invoke`/`Message`, the `SetMember` hook, text capture and retitling |
| `panels.*` | The hideout-style dock panel (`Records`), live score panel, results panel |
| `uilog.*` | Records every UI call the game makes (research; `uilog on`) |
| `input.*`, `psinput.*` | One place for controls: action -> button for the device in use, keyboard + XInput + PlayStation HID |
| `portal.*` | The player-facing flow: dock circles, travel with fade, starting runs, ini file, abandon prompt, post-run return |

## What a run looks like

```
portal thread: hero stands on a dock circle -> panels::Records (best run + goals)
  interact -> FadeTeleport to Ryker's arrival point; portal "armed" (g_armed = venue)
  hero crosses the start line -> portal::StartRun builds director::Options from the ini
director::Start -> director thread Run():
  preload the pool's actors (spawn::Preload; plan::BudgetedPool picks factions within a unit-type budget)
  countdown -> for each wave:
      plan::Make(cfg, wave, rng)  -> counts, mix, caps, bosses
      spawn rings out of the camera cone (director spawn rules, below), each enemy engaged with the hero
      Update(): kills, stuck enemies, stationary relocation, body pool culling, boss watchdog
      wave cleared -> boons::OnWaveCleared (pick 1 of 3; the fight is frozen via timescale)
  hero down / abandon / stop -> FinishRun: score, results, cleanup, OnRunEnded callback
portal thread: after the run, back to the arrival point; results panel until Continue
30 s after the run: spawn::ReleaseAll (assets are never released mid-run, see GAME_INTERNALS)
```

### Director spawn and cleanup rules (all in `director.cpp`)

- Minimum 18 m from the hero; points in the camera's view only at 45 m or more (camera cone about 78 degrees); enemies
  are placed on the game's own designer spawn points inside the yard.
- Stationary rule: an enemy more than 25 m away that stays still for 20 s while hidden is moved 12-30 m from the hero, out of view.
- Never-left-spawn rule: melee 25 s, ranged 45 s without leaving the spawn point; the point (and 4 m around) is avoided for the
  run and the enemy is removed once out of view and replaced (not counted as a kill).
- One capped pool (`[run] body_pool`, default 150) shared by live enemies and corpses. Bodies stay on the ground and are only
  despawned out of camera view; if the player is looking at bodies due for removal, spawns steer to the other side.
- Enemies killed by other enemies don't count as kills; Campaign gives the spawn back.

## Files the mod reads and writes

**Settings and records** live in `DataDir()` = `Documents\Marvel's Spider-Man Remastered\EndlessMode\` (see `paths.h`). They must not live in the game's `scripts\`: Overstrike wipes and recreates that folder on every Install mods (it reset the ini and deleted every record on 2026-10-16). On first run a version that kept them in `scripts\` is migrated (`MigrateDataFromScripts`). **Dev files** (the command file, logs) stay in `<game>\scripts\`.

In the data folder:

| File | Purpose |
|---|---|
| `EndlessMode.ini` | Player-facing settings; written with defaults on first launch. Also stores circle positions and the last dock used |
| `EndlessMode.cmd` | Dev command input (see GETTING_STARTED) |
| `EndlessMode.log` | Main log, truncated each launch |
| `EndlessMode_uilog.txt` | UI call recording (`uilog on`) |
| `EndlessMode_runs/run_*.json`, `runs.csv`, `stress_*.csv` | Telemetry, viewable in `tools/runviewer` |
| `EndlessMode_loadout.txt` | Saved suit loadout while a Campaign run is active (restored at run end, or on next launch after a crash) |
| `EndlessMode_horde_best.txt`, `EndlessMode_horde_scores.csv`, `EndlessMode_campaign_best.txt` | Records (best scores and Horde history) |

## Conventions worth knowing

- **No magic addresses outside `natives.cpp`/documented structs.** Offsets inside game objects are named constants or
  commented with where they came from.
- **Deliberately leaked memory**: GFx values held by `gfx.cpp`'s text capture are heap-allocated and never freed; the game's
  HUD teardown releases them. Freeing them ourselves crashed the game. See the comment in `gfx.cpp`.
- **Never release assets mid-run.** Releasing a model while enemies using it are alive made survivors bodiless and
  crashed the game. Assets are released only 30 s after a run ends.
- **Pure functions where possible.** `plan.cpp` and parts of `score.cpp` have no game dependencies, which is why they can be
  tested offline.
